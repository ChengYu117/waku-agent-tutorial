## 二、考官意图与核心逻辑链（大白话拆解）

### 1. 消息重复的来源、幂等占位失败怎么办，以及冷热分层存储（Q2）
- **考官想验证什么**：你知不知道“为什么队列会发两遍”、用 Redis 拦重万一挂了怎么办，以及大数据量为什么要拆冷热库。
- **大白话逻辑链**：消息重复就像送快递三处都可能重：发货方没听到回执重发、快递站等不到签收重派、收件员半路重启重干。光靠 Redis `SETNX` 拦重有个致命坑：刚占好坑位进程崩了，如果没设过期时间，这条消息就永远卡死无人再处理；而跨存储分层（热数据放 Redis、温数据放 MySQL、历史冷数据放对象存储）是因为一个大表塞几亿行会让索引深、备份卡死，写一致性要以 MySQL 为唯一事实源再异步同步外层，失败靠对账补救。
- **三层追问与雷区**：为什么不单靠消费端确认 → 占位死锁怎么破 → 分层后跨库一致性如何兜底。**雷区**是只背“用 Redis 去重”却答不出占位过期与业务失败回滚。

### 2. 多 Agent 拆分边界与边际收益递减（Q3）
- **考官想验证什么**：考官反感“为了时髦强行塞五六个 Agent”，他在考你懂不懂多 Agent 的延迟和成本代价。
- **大白话逻辑链**：一个厨师能搞定的家常菜，硬拆成洗菜工、切菜工、炒菜工、摆盘工传话四遍，反而上菜慢、沟通丢信息。拆多 Agent 只有三个正当理由：上下文和工具列表必须隔离（放一起太乱选错工具）、读写权限必须隔离、子任务互不依赖可以并发加速。不能无限加角色——每多一次交接就多一次信息失真和延迟翻倍，必须靠评测数据验证拆比不拆更好。遇到大模型超时或超预算，按“先退避重试（只限可重试错误）→ 换轻量小模型/减上下文/跳非核心步骤降级 → 实在不行明确提示失败”，并盯着任务成功率、P95 延迟、单次成本去调优。

### 3. 线程池 7 参数反常识追问与慢 SQL 排查（Q4–Q5）
- **考官想验证什么**：看你是死背 7 个名词，还是真明白线程池内部 `Worker` 是怎么运作的。
- **大白话逻辑链**：提交流程像窗口办业务：先开核心窗口 → 坐满去等候区队列排队 → 排队也满才临时加开机动窗口（到最大线程数）→ 还挤不下触发拒绝策略。因此无界队列会让“最大线程数”形同虚设。至于“核心线程知不知道自己是核心的？”——其实工人牌子上根本没写“我是正式工”，池子只在人闲下来想裁员时，数一下当前总人数有没有超过核心定编，超了就允许超时下岗。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| 队列幂等、限流与防过载 | BullMQ 异步队列 + 速率/内存守护机制 + 任务状态记录，防止单个租户突发大批任务拖垮 Worker | `有证据` | 对照说明异步任务如何防重与保护下游资源 |
| 冷热分层与大结果外置 | 对话大输出不塞数据库对话历史或模型上下文，超限自动溢写到外部文件存储并保留分页查询句柄 | `有证据` | 可类比“冷热大体积分离”，但明确说明 Twenty 主业务表仍在 PG |
| 多 Agent 协作团队 vs 单 Agent | Twenty 当前主打单 Agent 深度执行循环（Prompt 缓存 + 渐进 Skill/Tool），未做复杂多 Agent 协同编排 | `无证据` | 诚实讲清“何时适合单 Agent+Skill 渐进加载，何时才需要拆分多 Agent”，非常加分！ |
| 超时降级与线上评测指标 | 有基础步数上限、流式取消和内置评估执行器骨架，缺线上真实业务指标 | `部分证据` | 讲清设计思路，指标数字标 `待确认` |
