## 二、考官意图与核心逻辑链（大白话拆解）

### 1. LangGraph 的本质：有环持久化状态机（vs 线性 Chain），以及 Checkpoint 的坑（Q4）
- **考官想验证什么**：你选 LangGraph 是因为别人都在用，还是真理解“有环循环”“增量 Reducer 防覆盖”“Checkpoint 恢复时的非确定性副作用陷阱”。
- **大白话逻辑链**：普通脚本一条道走到黑（线性 Chain），但真业务经常要“查资料发现不够 → 改写问题回去重查 → 关键一步停下来等人批准 → 再接着走”，这就需要一个能拐弯循环、还能随时保存进度的图状态机。**设计共享 State 有三原则**：只有跨步骤共用的数据才放进去；对话列表这类追加字段必须明确用“追加合并规则”，否则一步执行完直接把老记录全覆盖没了；**千万别把数据库连接、Client 实例这种没法序列化存盘的东西塞进 State**。至于 Checkpoint 快照最大的隐藏坑：**恢复重放时，节点里如果写着发邮件、扣款这类外部动作，重跑一遍就会发两次邮件**，所以副作用必须防重或放受控代码层！

### 2. 知识图谱补「多跳连线」，向量 RAG 补「原文细节」（Q5–Q6）
- **考官想验证什么**：做过图谱 RAG 就必须讲得出它赢在哪、输在哪，而不是吹它包治百病。
- **大白话逻辑链**：普通切片 RAG 就像把一本书撕成一页页放进抽屉，想找“哪几家子公司的产品用到了 X 技术”这种要跨越两三个抽屉连线的问题，普通切片常常凑不齐线索。知识图谱专门把“实体—关系—实体”画成关系网，按图索骥连跳一两步就把证据链串出来了。代价是抽图谱贵、结构更新麻烦，所以工程里是**图谱负责补关系路径，文本向量负责捞原文证据**，联手重排。

### 3. 测试集来源、CI 回归 Diff 与首 Token 延迟拆解（Q8–Q9）
- **考官想验证什么**：拒答题有没有放进测试集，以及怎么优化用户面对大模型时的“体感卡顿”。
- **大白话逻辑链**：优化延迟先把时间切片（意图识别 + 检索 + 重排 + 模型首字时间 + 吐字总耗时 + 多轮往返）：能并行的检索和路由同时跑、热问题缓存、小模型干路由改写、大模型只管最后收口，再用流式输出先把第一个字（TTFT）在两秒内顶到用户眼前。另外，绝对不能声称别人开源的模型是自己训的（Q7 红线）。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| 有环可暂停/恢复的状态流与 HITL 人工打断 | Twenty 原生实现了 `agent-run-suspension`（类似 `interrupt` 挂起待人确认再唤醒继续）与可控步进循环，但采用 TypeScript 工程化自研循环而非 Python LangGraph | `有证据` | 对比说明“自研状态循环 + 挂起唤醒”与 LangGraph Checkpoint 在思想上高度相通 |
| State 序列化保存与非确定性副作用防重 | 对话消息与运行状态按步持久化到 PG；对外部工具执行记录状态以配合断点恢复 | `部分证据` | 重点答出“可序列化约束 + 重放副作用幂等意识” |
| 知识图谱构建、多跳 RAG 对比及微调模型 | Twenty 无知识图谱、无向量 RAG、未自行微调大模型 | `无证据` | **铁律**：严禁把开源或第三方大模型说成自训模型；图谱 RAG 按场景设计原则应答 |
