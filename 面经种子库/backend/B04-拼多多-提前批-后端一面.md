## 一、本场真实面试题清单（忠于原帖）

1. Agent 与 LLM 的超时怎么处理？
2. 消息顺序、重复消费和丢失，分别怎么处理？
3. 数据库与缓存的一致性，怎么保证在约定范围内？
4. 接口平均耗时从 200ms 变成 5s、CPU 也飙升了，怎么排查？

## 二、考官意图与核心逻辑链（大白话拆解）

### 1. Agent/LLM 两层超时预算与「超时 ≠ 没成功」（Q1）
- **考官想验证什么**：写多步 Agent 链路时，知不知道串行超时会叠罗汉，以及外部工具一旦超时、你敢不敢直接重试。
- **大白话逻辑链**：多步 Agent 就像接力赛跑，总时间只有 30 秒，第一棒花掉 12 秒，第二棒就只剩 18 秒预算（传递全局截止时间 Deadline），不能每一棒都各自允许等 30 秒，否则用户等两分钟早就关网页了。更重要的是，调用外部建单工具超时，只说明“回执没传回来”，不代表对方没把单建好；如果盲目再调一次，就会多出一张重复工单。正确动作是每次调用前先生成唯一业务幂等单号，超时后拿这个单号去对方系统查状态，确实没做成才补发。
- **三层追问与雷区**：全局预算分配 → 读操作与写操作重试差异 → 外部系统无查询接口时的兜底（进状态未知队列人工或对账）。**雷区**是答“统一设个 30s 超时，失败就重试 3 次”。

### 2. MQ 顺序、重复消费与丢消息三段闭环（Q2）
- **考官想验证什么**：高并发异步系统里，“刚改完数据库还没来得及跟队列确认就断电重启”这类经典边界怎么兜。
- **大白话逻辑链**：MQ 问题永远分三段看：
  1. **顺序**：现实不做全局排队，只保证“同一订单/同一个用户”的包裹按同一根传送带（同分区主键）由单个工人串行拆包。
  2. **重复**：哪怕消费完再提交确认，工人刚把货放进仓库（DB 提交成功）突然停电，队列没收到回执，重启后还会再发一遍。所以消费端自己必须认“业务唯一号”，重复进来直接忽略或靠状态机拒掉非法回退。
  3. **丢失**：发货端不能写完库就撒手不管（用本地消息表或事务消息防发出前断电），队列自身要持久化加多副本，消费端必须干完活再手动确认。
- **三层追问与雷区**：顺序粒度取舍 → 落库已成功但 ack 丢了怎么防重 → 生产端写库与发消息非原子怎么解。

### 3. 缓存与 DB 一致性的真实边界：「约定窗口」（Q3）
- **考官想验证什么**：你是否清醒地知道分布式系统里“绝对零延迟强一致”不现实，以及如何控制最终一致的窗口宽度。
- **大白话逻辑链**：标准动作是“先改数据库，再删缓存”。为什么不顺便改缓存？因为两个人同时写，慢的那个可能把旧值后覆盖上去。如果删缓存那一下网络抖了失败，就要靠重试队列或订阅数据库变更日志（binlog）异步补删。至于真正“零容忍刚写完马上就要读到最新”的极少数动作，直接让它去读主库，而不是为了面子给所有读请求上重锁。

### 4. 接口 200ms 变 5s 且 CPU 飙升排障顺序（Q4）
- **考官想验证什么**：线上救急时是靠瞎猜乱重启，还是按证据链逐层缩圈。
- **大白话逻辑链**：标准四步走：① 先划边界（全站慢还是单机慢、何时开始、是不是刚发版或流量暴涨）；② 拆分段耗时（网关、业务服务、DB、缓存各自占了几秒，先判断是自己算得慢还是傻等下游）；③ CPU 飙高证明自己机器在疯狂空转（抓线程栈或火焰图看是不是死循环、正则回溯、疯狂 GC 或锁抢占；如果 CPU 很低却慢，八成在等慢 SQL 或下游）；④ 先限流/降级/回滚止血，再修根因，不能只回滚不复盘。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| Agent 超时控制、防重复写与步数预算 | Agent 主循环有 `MAX_STEPS=300` 硬上限、工具执行容错与前端流式防重续跑，但针对外部第三方不可幂等写工具的“执行意图落表+超时反查”可扩展补充 | `部分证据` | 讲清已有步数/状态保护，同时明确写工具超时不能盲重放的边界 |
| Redis 缓存与 DB 一致性窗口 | 具备事务后统一触发清理缓存与发事件机制，避免事务未提交前旧数据被污染 | `有证据` | 重点讲清“为什么事务提交后才删缓存”与读写并发取舍 |
| 消息顺序/防丢/消费幂等 | Twenty 用 Redis+BullMQ 做异步任务队列、任务按租户与队列规则调度；无 Kafka 分区模型 | `部分证据` | 围绕通用 MQ 三段防丢+幂等表思路作答，对照 BullMQ 说明队列定位 |
| 接口 200ms→5s + CPU 飙升线上排查 | 属于线上排障方法论场景题，需结合排障流程回答（非 Twenty 现成故障经历） | `待确认` | 绝不虚构自己在生产环境排查过 5s 故障，按场景题拆解步骤 |
