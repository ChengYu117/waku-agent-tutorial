## 二、考官意图与核心逻辑链（大白话拆解）

### 1. Harness 本质与「压缩控制权必须在 Harness 手里」（Q04–Q06、Q08）
- **考官想验证什么**：2026 年底 Agent 面试最高频的区分度问题——你是否理解“模型只是大脑，外面的 Harness 才是手脚、神经反射和仪表盘”。
- **大白话逻辑链**：一句话分清：**模型决定“我想做什么”，Harness 决定“实际允许做什么、怎么做完验收、失败了怎么收拾残局”**。最典型的反直觉考题就是第 5 题：“上下文快满了，是谁决定触发压缩的？”答案**一定是外面的 Harness 代码按 Token 比例或轮次阈值硬触发，绝不能指望模型自己“自觉举手说我记不住了”**——模型自己判断压缩既不可靠、也守不住成本红线。
- **记忆四层大白话**：按“新鲜度 + 谁来读”切分：最近几轮留原文给模型看细节 → 较早对话压成决策摘要给模型看主线 → 再早期压成任务结论表 → 最外层跨会话的规则文件和记忆库留给下一次开新对话用（并记得保留关键报错原文和文件路径防失真）。

### 2. 多 Worker 异步并发改同一份代码的冲突分水岭（Q03）
- **考官想验证什么**：分派任务谁都会说，考官真正要挖的是“两个子 Agent 同时改同一个文件把彼此修改覆盖掉怎么办”。
- **大白话逻辑链**：就像多人协作写项目，绝不能让两个工人对着同一份活文件直接覆盖保存。四重办法：① 派任务前按目录或文件范围划清地盘（依赖编排）；② 隔离施工，每个 Worker 分在独立隔离目录或分支（如 git worktree）里改；③ 写入用版本号乐观锁校验，别人动过了就重读冲突；④ 最终合并以“跑通测试验证过的版本”为准，而不是谁最后写就算谁赢。

### 3. Goal Loop 闭环评测如何防止「假成功」（Q02）
- **考官想验证什么**：看你测“自己改错直到完成”的循环时，是不是只看模型嘴上说“我修好了”。
- **大白话逻辑链**：必须用可程序自动执行的验收门禁（单测跑通、命令退出码、文件校验）判定达成率，配合轮次效率和消耗成本三件套；专门建一批测试“提前嘴硬说完成、反复改同一行死循环、无视报错”的负样本。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| Harness 运行时控制循环与触发权 | Twenty 的 Agent 执行主循环完全在服务端代码掌握中：含上下文占比达到 90% 自动触发消息剪枝、步数硬限制、工具修复与预算控制 | `有证据` | **完美印证第 5 题！** 直接举出“上下文使用达到约 90% 阈值由 Harness 主动触发剪枝”的真实设计 |
| 四层记忆压缩 vs 单会话裁剪 | Twenty 实现了单会话内基于阈值的消息剪枝与大结果溢写，但尚未做跨会话长期结构化记忆沉淀 | `部分证据` | 诚实划出“当前做到会话内裁剪、未做跨会话长期记忆”的边界 |
| 多 Worker 并行改文件（worktree/乐观锁） | Twenty 无多 Worker 并发写文件架构 | `无证据` | 按系统设计思路回答隔离与乐观锁策略 |
| Goal Loop 自动化验证门禁 | Twenty 有原生评估运行器基础骨架，但缺少针对业务目标的完整自动化回归集 | `部分证据` | 讲清“确定性验收条件 > 模型自评”的评测原则 |
