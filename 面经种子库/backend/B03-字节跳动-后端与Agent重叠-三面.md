## 二、考官意图与核心逻辑链（大白话拆解）

### 1. 业务本体建模 vs 「CLI + Skill」路线对比（Q13–Q18）
- **考官想验证什么**：三面考的是技术决策判断力——你能不能说清“为什么不把数据库表直接扔给大模型操作”，以及“先搭统一业务模型”和“快速包成工具+说明书（Skill）”各自的适用期与代价。
- **大白话逻辑链**：数据库表就像后厨账本里的缩写代码和拆分明细，一次“推进候选人进下一轮”可能涉及改三张表和五条隐性规矩，直接暴露表结构给 AI，AI 根本不知道不能乱改已结束的面试评分。所以要把能力抽象成**业务能听懂的动作（Action）**，粒度正好对应“人能一句话说清的一件完整业务事”。至于“先做统一本体建模”还是“CLI + Skill 快速上”，前者像建统一普通话和标准插座，安全可审计但前期改造成本重；后者像给老工具贴使用说明书（Skill），接入飞快但工具一多容易同义不同名、权限分散。存量老系统动不起时，可以先只做“读侧统一语义视图”，写操作继续走老接口。
- **三层追问与雷区**：为何不能直接映射 DB → Action 粒度标准 → 两种路线取舍与老系统兼容。**雷区**是只夸新方案好、完全不提重构成本与适用边界。

### 2. 效果指标口径与「旧方案 vs 初版」辨析（Q06–Q12、Q19）
- **考官想验证什么**：识别候选人是不是在用“自己第一版故意写烂的 demo 当基线”凑出一个好看的提升百分比。
- **大白话逻辑链**：指标必须三件套齐备：基线是什么（原生产旧方案，还是自己 v0.1 雏形）、样本量与抽检方法（怎么标注、是否双人复核）、以及分母周期。只有跟真实旧方案比才叫替换收益；跟自己初版比只能算迭代收益，混在一起报在三面会被一追到底直接识破。

### 3. 个人边界、导师分工与真假项目识别（Q20–Q25）
- **考官想验证什么**：终面核心筛查——把“团队做了什么”和“你本人到底拍板写了哪一块”剥离清楚。
- **大白话逻辑链**：用“我负责哪段接口/数据流边界 + 当时遇到什么选型纠结我怎么定 + 怎么验收”讲清楚，主动把不是自己主导的模块划给导师/团队，可信度反而陡增。同时把“开源/个人练手项目”和“真实上线产生业务效果的项目”明确区分开，不把练手成绩吹成生产收益。

### 4. 计算机底层常识抽检（Q29–Q31）
- **考官想验证什么**：即使做 AI 应用方向，后端底线（进程线程隔离成本、内存划分、TCP/UDP 边界）不能空白。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| 为何不能直接让 AI 操作数据库表（需要业务语义层） | Twenty 核心引擎有标准元数据对象模型（Object/Field Metadata）和 RBAC 权限层，Agent 必须通过封装好的业务工具或工作流动作操作数据，而非裸写 SQL | `有证据` | 这是极强加分项！直接对应 Twenty 的元数据对象与工具封装哲学 |
| 业务建模 vs Skill 渐进式路线对比 | Twenty 同时具备结构化 CRM 业务对象模型与原生 `Skill` 渐进式加载模块，正好体现了“核心实体走模型契约、专业流程走 Skill 说明书”的混合折中 | `有证据` | 用大白话讲清“核心实体统一 + 长尾流程靠 Skill 按需注入”的双轨思路 |
| 个人项目/研究边界与量化评测基线 | Twenty 是开源上游项目；候选人个人研究/二开边界与量化对比数据目前未实测 | `待确认` | 严禁把 Twenty 上游设计说成“我独立主导并拿到 XX% 线上提升” |

## 四、沉淀到 `/asu-skills` 的 Claim 种子

- `[Architecture]` “核心对象元数据建模 + Skill 渐进加载”与单纯数据库直连方案的取舍及 Action 粒度设计（对应 `asu-training-seed.md` -> `seed-ag-01`、`seed-ag-04`）
- `[Ownership]` 明确区分开源项目上游架构设计 vs 个人学习验证/二次开发边界（对应 `seed-be-10`）
- `[Metric]` 任何“准确率/耗时提升”指标的基线来源（旧方案 vs 初版）、样本数与统计口径（对应 `seed-be-10`、`seed-ag-09`）
