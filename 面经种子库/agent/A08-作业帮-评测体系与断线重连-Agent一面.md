## 二、考官意图与核心逻辑链（大白话拆解）

### 1. 前端刷新/断网重连，如何保证流式对话一字不丢、不重复？（Q2–Q3）
- **考官想验证什么**：这是 AI 应用高频必考题——“模型正吐半截字，用户坐地铁断网或关掉重开网页，怎么接着看后面的输出，又不会两台机器重复跑”。
- **大白话逻辑链**：靠三条配合：
  1. **消息别只攥在内存连接里，先持久化编号再发**：服务端给每条消息甚至增量片段编上递增序号（或游标），边生成边存起来，前端手里记着“我已经收到的最大序号”；断线重连后前端亮出这个序号，服务端精准补发后面的尾巴并按号去重。
  2. **跨机器路由与共享广播**：重连时请求可能打到另一台服务器上，所以正在跑任务的 Worker 要把实时流广播到共享频道（如 Redis PubSub）或者把任务状态存在共用数据库里，让新接入的机器能接力吐流。
  3. **心跳检测与断线兜底**：后台定时写心跳确认活着；正在生成中的半成品消息也要可续写或按断点接管。

### 2. 「先硬指标一票否决，再 LLM 评审算软分」的分层评测闭环（Q5–Q13）
- **考官想验证什么**：拒绝模糊的感觉评价，要把线上真实抱怨（Oncall）变成能定位具体责任层的自动化仪表盘。
- **大白话逻辑链**：把一次对话的每步思考、工具出入参和耗时全量抓进 Trace 审计表里。跑评测时先算**代码能直接拍板的硬指标**（工具一共调了几次、有没有误触禁用高危工具、参数格式对不对、Token 和总耗时多少）——**只要硬指标挂了（比如越权或死循环），直接一票判负**；硬门槛过了再请裁判模型（Agent Reviewer）按维度打软质量分（记得定期找人抽检校准裁判偏见）。一旦发现低分错例，立刻归类到“工具说明写得烂 / Skill 流程绕 / 检索没捞到 / 模型脑子不够”，精准修哪一层，并把修好的坏例子固化进回归题库防止改一处坏一片。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| **第 3 题：前端断线重连、流式恢复与心跳抢占** | Twenty 原生内置极其扎实的 `agent-chat-stream-recovery` + `agent-chat-cancel-subscriber`：通过 PG 存储状态、Redis 缓存/PubSub 广播与取消、DB CAS 抢占及僵尸心跳回收，完美支撑断线重连和刷新续看 | `有证据` | **压箱底强项！** 把 Twenty 这条完整断线续推和防双活链路用大白话讲透，能直接拿高分 |
| 工具调用审计与执行记录 | 每次工具调用出入参、步数、状态与 Token 消耗均入库可查，配合步数账单统计 | `有证据` | 对照 Q4 审计与 Q9 Token/工具统计回答 |
| 原生评测运行器 vs Oncall 分层迭代体系 | Twenty 有原生评估运行器基础模块（`ai-evaluation`），但尚未建立线上 Oncall 自动沉淀回归集和人工校准的 Agent Reviewer 报告系统 | `部分证据` | 诚实讲出已有运行器基础，具体“多少条 Case、人工保留率”绝不乱编（标 `待确认`） |
