## 二、考官意图与核心逻辑链（大白话拆解）

### 1. Redis 缓存设计、版本灰度与回源防雪崩（Q01–Q12）
- **考官想验证什么**：你是否真的把缓存放进过线上复杂业务里，而不是只会背“穿透、击穿、雪崩”三个名词。
- **大白话逻辑链**：缓存就像餐厅提前备好的半成品菜。Key 的命名就像贴标签（`版本号 + 实体维度`），新老版本同时上线放量时，靠版本号把新旧菜品天然隔开，互不串味。刚切到新版本时新缓存是空的，如果不加保护，所有食客都会直接冲进后厨（数据库/模型服务）把后厨挤爆——所以要先做热点预热、按比例灰度放量、并发回源合并（单飞），并留着旧版本缓存兜底。
- **三层追问与雷区**：第一层问 Key 设计与数据结构取舍；第二层问切换瞬间的回源冲击怎么防；第三层问 TTL 怎么定、命中率怎么量化、旧缓存怎么评估影响。**雷区**是报不出合理排查口径或盲目吹嘘“99% 命中率”。

### 2. 服务耗时排查、异步日志与过滤前置（Q13–Q20）
- **考官想验证什么**：遇到接口变慢时有没有系统排查顺序，以及工程优化时会不会踩“内存复用串数据”的隐蔽坑。
- **大白话逻辑链**：把同步打日志改成异步，就像服务员记完菜单后随手丢进出菜小盒，不用自己跑到后厨等厨师写回执。但要注意“点菜单板（context 对象）”如果是循环复用的，服务员刚把单子递给后厨就擦掉重用，后厨看到的就变成下一桌的菜了——所以入队前必须拷贝所需字段，或者等打印完再归还对象。看收益重点盯 P99（最慢的那 1% 请求），平均值容易把尾部卡顿藏起来。
- **三层追问与雷区**：从定位瓶颈 → 异步队列改造 → 对象池复用冲突 → 队列满了怎么兜底。**雷区**是只说“平均耗时降了”，却忽略队列积压丢日志和对象复用串数据。

### 3. 慢 SQL 排查、索引底层与 InnoDB MVCC（Q21–Q38）
- **考官想验证什么**：SQL 慢了怎么一步步抓凶手，以及数据库如何在多人同时读写时既不互相卡死、又不丢数据。
- **大白话逻辑链**：N+1 查询就像去超市买 10 样东西跑了 10 趟，改成一次 `IN` 批量拉取就能省掉大量往返。对字段套 `CAST` 类型转换就像把书名先翻译成外文再查目录，书架索引目录直接作废。MVCC 则像“给每个进门看书的人拍一张瞬间快照（ReadView）”：有人同时在改书里的字（新版本写进 undo log 版本链），你看快照时只认拍快照前已经提交定稿的那一版；“读已提交”每查一次拍一次新快照，“可重复读”整个事务共用第一张快照。
- **三层追问与雷区**：从慢 SQL 排查流程 → 各种索引失效动作 → MVCC 三件套与隔离级别差异。**雷区**是把 MySQL 的隔离级别与实际工程（如项目用的是 PostgreSQL）混为一谈。

### 4. 语言容器、事务失效与双层限流（Q39–Q47）
- **考官想验证什么**：并发控制基本功（入口挡一刀 + 下游资源再兜底），以及常用语言集合/事务注解边界。
- **大白话逻辑链**：双层限流就像景区管理：大门口先按人头发放门票或令牌桶放行（挡住外围突发洪峰），里面热门小馆再靠有限座位和排队队列（信号量/线程池）保护自己不被踩踏。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| Redis Key 隔离与单飞防回源 | Redis 缓存模块支持租户隔离命名空间，并在回源时使用 Singleflight 并发合并、防缓存击穿与大对象防爆处理 | `有证据` | 重点讲清“为什么多租户缓存要防单飞击穿与版本/数据失效” |
| 事务提交后再执行外部副作用 | 工作流与数据库上下文通过事务后回调钩子，保证事务真正落盘后再发消息或清理缓存 | `有证据` | 结合“数据库与缓存/消息一致性”说明边界 |
| 慢 SQL、N+1 与索引原理 | Twenty 使用 PostgreSQL 与自定义查询引擎，存在批量预加载及元数据表索引机制（非 MySQL） | `部分证据` | 讲清通用 MVCC/N+1 逻辑，同时诚实说明本项目底座是 PG、无 MySQL 线上调优数字 |
| 异步日志与真实 P99 观测 | 具备基础日志与请求上下文追踪，但未经过大流量压测取得真实 P99 优化数字 | `待确认` | 不可编造优化前后的 P99 毫秒数，可从设计角度谈异步降阻塞 |
| 双层限流与任务并发控制 | BullMQ 任务队列具备分组速率限制器与内存守护限制，保护异步 Worker 不被打垮 | `有证据` | 对照“网关限流 + 消费端限流”展开讲解 |
