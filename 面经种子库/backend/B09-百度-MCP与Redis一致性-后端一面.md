## 二、考官意图与核心逻辑链（大白话拆解）

### 1. MCP 工具选择与 Skill「渐进式披露」（Q02–Q08）
- **考官想验证什么**：现在后端面经已经高频追问 MCP 和 Skill，考官想听清楚客户端是怎么启动握手、怎么在几十上百个工具里不把提示词塞爆。
- **大白话逻辑链**：MCP 就像电脑上的 USB 标准接口，连接服务端后先拉取一张“工具目录卡片”（包含名字、作用说明、入参格式）。但目录卡片和详细操作手册如果一上来全部印进系统提示词，就像进餐厅一次递给你十本百科全书，模型又晕又费钱。**渐进式披露**就是先只给一张薄薄的菜单目录（名称 + 一句话摘要），模型看中某项技能时再按需去翻那一页的详细说明和脚本，既省 Token 又大幅提高挑对工具的准确率。

### 2. Redis Lua 原子防超卖与热 Key 治理（Q12–Q14）
- **考官想验证什么**：单机并发秒杀扣减时为什么一定要用 Lua，以及热 Key 压垮单台 Redis 节点怎么办。
- **大白话逻辑链**：如果让业务代码先问 Redis“还剩几个？”，再喊 Redis“减一个！”，高并发下两个人同时问到“还剩 1 个”，就会一起扣成负数。Lua 脚本就像把“查余额 + 扣减 + 记流水”打包成一张不可插队的连续动作卡，交给单线程执行的 Redis 一次性一口气跑完。遇到某个爆款 Key 流量冲垮单个分片时，通常靠本地进程内存兜一层热点缓存，或者把热 Key 拆散备份分摊请求。

### 3. 灵魂追问：「照着标准写法做，为何还会长达 10 分钟不一致？」（Q15–Q16）
- **考官想验证什么**：考官故意放过常见的“毫秒级并发读写冲突”，专问三分钟、十分钟的持久不一致，查你有没有真线上排查直觉。
- **大白话逻辑链**：如果只是读写并发撞车，也就影响那么一刹那或者等缓存过期。真能错上十几分钟，八成逃不出四个隐蔽凶手：① **删缓存失败了却没有重试补偿**，新旧值一直卡在里面；② **系统里还有另一条冷门写接口改了数据库却漏了删缓存**，大家全在盯主链路，根本没想到偏门入口改库没清缓存；③ **数据库主从同步卡了延迟几分钟**，某次读从库拿到老数据又写回了长缓存；④ **缓存压根设了极长 TTL 或忘了设过期时间**。排错时第一反应应该是“把所有写这张表的路径全都翻出来查一遍”，再用数据库日志（binlog）订阅做兜底补删。

## 三、与 Twenty CRM 项目的映射与边界

| 本场高频考点 | Twenty CRM 对应机制（大白话） | 证据状态 | 面试建议 |
| :--- | :--- | :--- | :--- |
| Skill 渐进式披露与工具按需加载 | Twenty 原生内置 `Skill` 渐进式加载和工具注册发现体系：日常只暴露轻量目录摘要，匹配后再加载详细指令 | `有证据` | 这是面试高频亮点，可直接对照真实模块流转讲透 |
| MCP 协议接入与多模式调度 | Twenty 支持 `meta` / `direct` / `generic` 等多种 MCP 调用模式，打通外部工具接入与参数校验 | `有证据` | 讲清“为何有的工具做元发现、有的直接暴露”的上下文权衡 |
| Redis Lua 原子脚本防并发乱序/超额 | Twenty 缓存与并发控制中使用 Redis Lua 脚本实现原子比较与替换（CAS），避免并发覆盖 | `有证据` | 类比讲清 Lua 在 Redis 原子组合操作中的不可替代性 |
| 多 Agent 无直接通信怎么保证协同 | Twenty 当前以单 Agent + Skill 路由为主，无复杂多 Agent 协同 | `无证据` | 诚实说明，回答侧重“输入输出契约 + 结构化校验”场景思路 |
